## Product doctrine

Decisions already made. Implement them; do not redesign them.

### The developer never leaves the editor

A developer's whole loop is: ask for a review, read it, argue with it or fix it, ask again. All of it
through the agent, in conversation. The web UI is for leads. If a task seems to need the developer
to open a browser, the task is wrong.

### A finding is a thing that persists, not a line of output

Every finding has a **fingerprint**: `sha1(rule_id + normalized file path + normalized content of
the offending line)`. Deliberately *not* the line number — code moves, and a finding that changes
identity every time someone adds an import above it can never be tracked, dismissed or confirmed
fixed.

A finding carries a **disposition**, scoped to the project:

| Disposition | Set by | Meaning | Effect on the next review |
| --- | --- | --- | --- |
| `open` | default | Nobody has answered it | Reported normally |
| `fixed` | developer | "I fixed this" | If it does not reappear → confirmed. If it reappears → back to `open`, and the review says the fix did not hold |
| `dismissed` | developer, reason required | "This is wrong or does not apply here" | Auto-suppressed, **visibly**, quoting who dismissed it, when, and why |
| `accepted` | lead only, reason required | "Real, but we accept it" | Auto-suppressed, visibly, and listed in the project's accepted-risk view |

A muted finding is never silently dropped. It appears in the review as suppressed with its reason.
Silence is what makes a tool untrustworthy: the developer must always be able to see what was hidden
and why.

### Arguing with a review is a first-class action, not a complaint

Findings are numbered `1..n` in what the agent shows. The developer talks normally — "3 is wrong, we
do that on purpose", "fixed 1 and 2" — and the agent turns that into one `smith respond` call. The
developer never types a command, an id or a JSON payload. Ever.

A dismissal is cheap for the developer and expensive for the rule: reasons are aggregated per
`rule_id`, and a rule dismissed repeatedly is surfaced to the lead as a bad rule. That is the
feedback loop that keeps precision up. **Dismissals are data, not defeat.**

### A review must be worth asking for

If the change is trivial (only files nobody reviews, or no substantive lines), say so and do not open
a review. A tool that produces ceremony for a typo fix gets uninstalled.

### Rules follow the project's platform version

Rules declare the versions they apply to. The plugin detects the version from the repository and the
server filters accordingly. A rule about an API removed in 2211 must not fire on a 2211 project.

### Deterministic quality is the moat

The LLM half is replaceable — every editor has one. What makes Smith worth paying for is that the
deterministic half is precise. A deterministic rule that cries wolf is worse than no rule: it burns
the developer's trust in everything else. **Precision over recall, always.** Every rule ships with
fixtures that prove both that it fires when it should and that it stays silent when it should not.

### [x] A4. Muting on re-review — done, commit 3094a3a

In `ReviewService.plan`, after scoping: any finding whose fingerprint has an active disposition of
`dismissed` or `accepted` is suppressed with reason
`"dismissed by <email> on <date>: <reason>"`, and excluded from the verdict.

`fixed` behaves differently and is the interesting case:

- Finding does not reappear → mark the disposition `confirmed_fixed`, and report it in the plan
  step as `fixed_confirmed: n`. This is the quiet reward for fixing things.
- Finding reappears → revoke the `fixed` disposition, report it normally, and set
  `regressed: true` on it so the agent can tell the developer the fix did not hold.

**Done when**: a fixture-driven test walks review → dismiss → review and shows the finding
suppressed with the quoted reason; a second test walks review → fixed → unchanged code → review and
shows it back as `open` with `regressed`. `scripts/e2e_browser.mjs` gains an assertion that a lead
can see the dismissal and its reason on the review page.

  `.gitignore`) **or** the diff has no added line with more than three non-whitespace tokens.

**Done when**: `node --test plugin/test` covers respond's happy path and its two refusals (no review
id, malformed stdin).

### [x] B2. The conversation, in `SKILL.md` — done, commit 93fd6dd

Rewrite `plugin/skills/review/SKILL.md` so the agent runs this loop:

1. `smith plan` → if `skipped`, tell the developer in one line and stop.
2. Reason over the diff, submit findings.
3. **Present the verdict first**, then the findings as a numbered list, shortest useful form: one
   line each, file:line, what to change. Blocking ones first. Suppressed ones are not shown unless
   the developer asks.
4. Then ask one question: *"Want me to fix any of these, or is something off?"*
5. Interpret the reply and call `smith respond`:
   - "fix 1 and 3" → apply the fixes, then re-run `smith plan`, then report the new verdict.
   - "2 is wrong because X" → `dismissed` with X as the reason. If the developer gives no reason,
     ask for one **once**, in one short sentence, and take whatever they say. Never lecture them
     about it.
   - "already fixed" → `fixed`.
6. Never argue with a dismissal. Never re-raise a dismissed finding in the same session.

Explicit rules for the agent: never print the raw JSON, never show fingerprints, never ask the
developer to run a command themselves, never report a finding count as an achievement.

**Done when**: the skill file describes every branch above, and `claude plugin validate ./plugin`
passes.

## Phase D — deterministic quality

This is the moat. Do not rush it, and do not trade precision for a bigger rule count.

### [x] D1. Rule fixture harness — done, commit 1d7d9d4

- `rules/fixtures/<case>/` containing `diff`, optional `files/`, and `expected.json`
  (`{"findings": [{"rule_id", "file", "line"}]}`, exact set).
- One pytest parametrized over every fixture directory. A fixture with an empty expected set is a

- At least three precision fixtures of ordinary, clean SAP Commerce and TypeScript code.

**Done when**: `uv run pytest -k fixtures` runs every case, and adding a rule without fixtures is
visibly incomplete.

### [x] D2. ESLint and dependency-cruiser analyzers — done, commit 5961217

Port from `projects-ai/reviewer/app/domain/services/external_analyzers.py`, adapted to the
files-on-disk model already used by `adapters/pmd.py`. Both degrade to `[]` when the binary is
absent. dependency-cruiser needs the full module graph, so it only runs when the plugin sent enough

**Done when**: a TS diff with a circular import produces one finding, and the analyzers are silent
on a machine without the binaries (a test forces the absent-binary path).

### [x] D3. A batch of genuinely good rules — done, commit 9d33cdb

Precision first. Each one needs a firing fixture and a precision fixture. Candidates, in order of
how often they are real problems:

1. Hardcoded credentials in **any** file type, not just `.properties` (extend the properties rule
   into a general secret scanner: connection strings, bearer tokens, private keys, AWS-shaped keys).
2. `catch` blocks that swallow — empty body or only a comment.
3. `printStackTrace()` and `System.out`/`System.err` in production code, excluding tests.
4. Spring XML: bean defined twice with the same id in the same file; `alias` pointing at a
   nonexistent bean in the same file.
5. ImpEx: `INSERT_UPDATE` without a unique key column marked, header/row column-count mismatch.
6. A query call inside a loop (the existing `context_pattern` mechanism already supports this).
7. `.gitignore`d file added anyway; a file over 1MB added to the repo.

Anything that needs cross-file knowledge to be correct is **out of scope** — that was the old
Intelligence server, and it is not coming back.

**Done when**: every rule has both fixtures, and the precision fixtures from D1 still pass with the
whole batch enabled.

as newly added) produced **348 findings — 39 per 1000 lines**. A 200-line change would land ~8
findings, most of them wrong. The synthetic fixtures did not catch this because the same author
wrote the rules and the fixtures, so they encode the same assumptions. Real code does not.

Until F1 passes, the deterministic half is a liability, not a moat. Nothing else in the backlog
matters more.

## Phase G — the conversation, actually exercised

Everything in phase B is written and nothing in it has been used. The `SKILL.md` describes six

largest untested surface in the repository.

### [x] G1. Scripted rehearsal of the whole developer loop — done, commit 9289062

`scripts/rehearse.mjs` — no LLM, just the CLI, so it is deterministic and can run every time:

1. Build a throwaway git repo from real corpus files (see F1 for the path), commit, then introduce a
   change that fires known rules.
2. `smith plan` → assert a review id, findings carrying `index` and `fingerprint`, and a verdict
   policy.
3. `smith respond` dismissing one finding with a reason → assert the verdict recomputes.
4. `smith plan` again on the same change → assert the dismissed finding comes back **suppressed**,
   quoting the reason, and does not affect the verdict.
5. `smith respond` marking another finding `fixed`, then actually fix it in the file → re-plan →
   assert `fixed_confirmed`.
6. Mark a finding `fixed`, change nothing, re-plan → assert it returns as `open` with `regressed`.
7. `smith review <id>` in a fresh shell → assert the plan can be recovered.

**Done when**: the script runs green from a clean database and asserts every step above. This is the
proof that the lifecycle in the doctrine actually works, end to end, on real files.

Measured 2026-08-21: `scripts/rehearse.mjs` runs **19 assertions green** against real postgres and a
repository built from six real corpus files, in about 90 seconds. Two deliberate breaks were run to
prove the assertions bite: dropping the `fixed` claim turns *"the review that met the fix records it
as confirmed"* red, and claiming a fix without making it turns that plus *"a finding reported fixed
and actually fixed does not come back"* red, with `regressed: 1` on the trail.

**A review submitted twice at once was leaving both submissions in the review.** `submit` reads the
review, replaces the agent's findings and re-rules, with nothing holding the row in between — so two
calls each read the state before the other wrote. Measured against real postgres over four rounds,
three of them stored 4 agent findings when each call submitted 2, and left two steps sharing
sequence number 2: findings nobody submitted together, an audit trail that collided, and a verdict
computed from neither half. `_own_review` now takes the row `FOR UPDATE`, which is the one place
both write paths already pass through. Eight rounds are clean with it and fail without it; sqlite
renders no `FOR UPDATE` at all, which is exactly why this case is proven on postgres.

**A 10,000-line file that trips one rule on every line produced 10,000 findings and a 4.1 MB
response**, stored in full and re-served on every read — a 460 kB diff in, 4.1 MB out, permanently.
The agent's findings were capped from the start (`max_agent_findings`); the deterministic half never
was. Now capped at 200, most severe first, and only when the cap actually bites — under it the order
a developer points at ("3 is wrong") does not move. 10,000 findings became 200 and 4.1 MB became
95 kB. What was cut is not silent: the agent's brief gains a paragraph naming the count, the rule and
the file, so the developer hears "9800 dropped, mostly `no-system-out` in `src/Flood.java`, that file
wants one sweep" instead of a list nobody reads.

**A 50 MB diff was buffered whole and then refused for being 25 times over the diff limit.** Same
body, same client, measured on the process high-water mark: 215 MB before, 50 MB after — and the
50 MB that remains is the in-process test client's own copy, not the server's. The check reads
Content-Length and answers 413 without touching the body; a tiny body with a huge declared length
proves the decision came from the headers alone. Chunked encoding, the way around a Content-Length
check, is refused rather than trusted.

**500 files was already refused, but the refusal carried the request back.** FastAPI's default
handler quotes the offending input, so a 45 kB request drew a 43.6 kB refusal and a 600 kB one drew
620 kB — and the plugin throws a structured `detail` away regardless, leaving the developer with
"it was not in the shape it expected". One sentence now: `files: list should have at most 400 items
after validation, not 500`, 66 bytes, which the plugin quotes as-is.

**The hanging analyzer was already bounded** and now has the test that says so: `run_json` cuts off a
subprocess that outlives its timeout, and a review whose analyzer times out still completes with its
rule findings intact. A rule that hangs needs no watchdog because the diff it runs on is capped —
measured at the 2 MB ceiling, the full ruleset over 110 files takes 0.23s, and a single 2 MB line,
the shape that would feed a backtracking regex, takes 0.21s.

Proven green: 89 pytest, 22 plugin, `next build`, 19 rehearsal checks, and 65 browser checks against
real postgres — the size check and the validation handler sit in front of every response the UI gets,
so the browser is what says they did not break it.

## Phase U — Pergamon, from a settled design to something a developer can run

`docs/pergamon.md` closes the decisions and this phase builds exactly what it describes and nothing
more. Read it before picking a task; it is short, and every "why is it not X" is answered there.

The decisions that bound every task below, so no task has to reopen them:

- **The server has no LLM.** Generation happens in the developer's editor. No providers, no cost,
  no egress to protect. Anything that needs a model on the server is out of scope by construction.
- **The server serves the catalog and records nothing.** No commissions, no answers, no generated
  code. What happens in the session stays in the editor and in git.
- **The web is read-only.** It shows the catalog. It cannot generate and it cannot author.
- **The same plugin.** A second skill in `plugin/`, no new install for anyone who has it.
- **Two things delivered:** the specs as conditions, and the code.

The measurement problem, stated once so no task pretends otherwise: Reviewer has a corpus and a rate
per 1000 lines. Pergamon has no equivalent yet and cannot be calibrated the way rules are. What
*can* be checked is that the surface behaves — tests, a real agent completing a real session, a
browser on the screen. Every task below is verifiable that way. The first honest calibration
arrives when generated code is fed back through Reviewer, and that is a later phase.

The entries are not invented. The previous Pergamon packaged thirteen features under
`~/Documents/commerce/projects/features/` and `features-best-run/`, each with a `feature.json`.
Those files are the input. They are outside this repository and are read, never written.
